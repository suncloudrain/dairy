## ADR-001：Flutter 支持 Android 与 Windows

- 日期：2026-10-07
- 状态：已采纳。
- 背景：项目用于个人日记和任务管理，目标设备为 Android 与 Windows，所有者正在学习独立开发完整应用。
- 决策：使用 Flutter 和 Dart，共用主要 UI、模型和业务逻辑；布局按可用窗口宽度适配。
- 理由：符合用户明确指定的技术和平台范围，减少同时维护两套业务实现的负担。统一规则便于学习和验证。
- 替代方案：分别使用 Android 原生和 Windows 原生技术，需要维护两套 UI 与平台集成；当前没有足够收益支撑增加学习成本。
- 代价：共享代码不等于平台行为相同。输入法、返回、窗口关闭、文件路径、数据库初始化和发行包都要分别验证。
- 重新评估条件：出现 Flutter 难以满足的明确平台能力或性能要求，而不是仅因为另一种技术流行。

## ADR-002：本地优先，SQLite 为 v0.1 数据来源

- 日期：2026-10-07
- 状态：已采纳。
- 背景：第一版不做云同步，需要断网可用和持久保存，数据有日期筛选、唯一性和状态一致性要求。
- 决策：日记和任务存入本地 SQLite；读写不依赖账号或服务器。数据库放在平台提供的持久化应用数据目录。
- 理由：SQLite 提供查询、索引、约束和事务，适合一天一篇、软删除、恢复冲突和任务状态更新。两张业务表足以表达当前需求。
- 替代方案：零散 JSON 文件需要自行处理安全写入、查询和唯一约束；键值存储不适合这些结构化查询；第一版建设服务器会增加部署、认证和故障处理工作。
- 代价：需要管理 schema 升级；两个设备上的数据库暂时独立。同步和备份界面不因本地优先而自动具备。
- 重新评估条件：同步阶段确定服务端方案时，增加远端能力；不能未经产品确认把本地读写改成依赖网络。

## ADR-003：sqflite 系列驱动，少量手写 SQL

- 日期：2026-10-07
- 状态：已采纳。
- 背景：需要兼容 Android 与 Windows，当前主要业务只有日记和任务两张表。
- 决策：Android 使用 sqflite，Windows 使用 sqflite_common_ffi；平台差异放在数据库初始化处。查询和数据对象转换先手写，不引入 ORM 或数据库代码生成。
- 理由：sqflite 提供 Android 支持，sqflite_common_ffi 提供 Windows 支持及相近 API。小规模 SQL 更容易看清数据读写和约束如何工作，降低首次开发的工具链成本。[sqflite 文档](https://pub.dev/packages/sqflite)、[sqflite_common_ffi 文档](https://pub.dev/packages/sqflite_common_ffi)
- 替代方案：Drift 等数据库抽象在类型化查询和响应式数据流方面有价值，但本项目暂时没有复杂查询或大量映射代码的需求；也可以统一走其他 SQLite 绑定，但没有必要同时维护多套访问方案。
- 代价：字段映射和 SQL 正确性需要测试保护。Android、Windows 的驱动初始化和发行构建必须分别验证。
- 实施约束：依赖版本按实际 Flutter / Dart SDK 兼容性选定并锁定；检查 Windows 原生 SQLite 库的构建和打包要求，不照搬旧版本说明。数据库路径使用 path_provider 和 path，避免硬编码路径。[path_provider 文档](https://pub.dev/packages/path_provider)
- 重新评估条件：表与查询明显增多，手写映射反复出错，或确实需要复杂响应式查询时，再评估是否引入 ORM。

## ADR-004：轻量分层，仓库统一数据入口

- 日期：2026-10-07
- 状态：已采纳。
- 背景：需要让初学者理解数据流，同时避免日记保存、恢复和任务状态规则散落在页面中。未来同步可能改变数据访问方式。
- 决策：区分页面、页面状态、数据仓库、SQLite 数据层；页面按日记和任务功能组织。普通 Dart 数据对象和日期规则可复用。v0.1 不另设通用用例层，不为每个动作建立类。
- 理由：界面负责显示，状态层协调交互，仓库提供统一规则入口，SQLite 层负责存取。可以分别验证保存调度和存储正确性，未来增加数据源时也有明确改动位置。这与 Flutter 官方分离 UI 和数据职责的方向一致。[Flutter 架构建议](https://docs.flutter.dev/app-architecture/recommendations)
- 替代方案：把 SQL 写在 Widget 中初期代码少，但日期冲突和保存规则容易重复；完整 Clean Architecture 加上逐操作用例类，会为当前规模增加较多跳转和文件。
- 代价：比全部写在页面中多一些连接代码，但责任更明确。分层只是代码约束，不自动保证业务正确。
- 重新评估条件：出现多个仓库共同参与且反复复用的复杂业务流程时，再考虑独立业务用例层。

## ADR-005：优先使用 Flutter 自带能力

- 日期：2026-10-07
- 状态：已采纳。
- 背景：当前只有有限的页面、列表和编辑状态，不需要复杂深链接或跨模块事件系统。
- 决策：页面状态优先使用 ChangeNotifier / Listenable，简单局部交互可用 setState；页面跳转使用 Navigator；依赖通过构造函数传入；复制正文使用 Flutter Clipboard API。
- 理由：避免同时学习多个框架。数据从哪里来、谁持有状态、谁调用保存都能从构造和方法调用直接追踪。ChangeNotifier 是 Flutter SDK 提供的可选状态通知方式。[Flutter 架构建议](https://docs.flutter.dev/app-architecture/recommendations)
- 替代方案：Riverpod、Bloc、路由包和服务定位器可解决更大规模的状态或组装问题，但目前没有明确需求证明额外依赖值得引入。
- 代价：需要自行管理监听、定时器和页面生命周期；简单机制同样需要规范和测试。
- 重新评估条件：复杂导航、多个模块共享状态或对象组装明显难以维护时，根据具体问题评估工具，而非一次性引入全套框架。

## ADR-006：每天一篇有效日记，UUID 与日期分离

- 日期：2026-10-07
- 状态：已采纳。
- 背景：用户确认每天一篇、可多次编辑，可补写和改日期，重复日期时提醒而不覆盖。
- 决策：日记使用 UUID 主键，日期单独保存；数据库只对未删除记录的日记日期建立唯一约束。所有新建、改日期和恢复路径都遵守该约束。
- 理由：UUID 是记录身份，日期是可修改的业务属性。软删除记录不占日期名额，使删除后重新写作成为可能；数据库约束为页面检查提供最终保护。
- 替代方案：用日期作主键会将身份与可变属性绑定；只在 UI 检查会让其他写入路径绕过规则；对所有记录强制日期唯一会阻止删除后重新写。
- 代价：恢复时可能出现冲突，需要保留双方记录并让用户处理。未来多设备离线分别创建同一天日记，也要专门处理冲突。
- 重新评估条件：用户明确改为每天多篇时，更新产品语义、导航和唯一索引，并保留原 UUID。

## ADR-007：日期与时刻分开，统一范围边界

- 日期：2026-10-07
- 状态：已采纳。
- 背景：日记日期和任务周期属于日历概念，创建、修改和完成属于具体时刻。月长、闰年、跨年和时区会影响计算。
- 决策：日记日期和任务范围保存为有效的 YYYY-MM-DD 文本；具体时刻使用 UTC 毫秒整数。范围统一为包含开始、不包含结束。
- 理由：业务日期不因时区转换偏移，具体时刻可以统一存储并按本地时间显示。不含结束边界可直接用下月月初、次年年初，避免“当天最后一毫秒”的特殊处理。SQLite 没有独立的日期时间存储类型，需要项目统一约定。[SQLite 类型说明](https://www.sqlite.org/datatype3.html)
- 替代方案：全部存成本地时间字符串会混淆时区；把日记日期存成午夜时刻容易在转换时改变所属日；使用包含最后时刻的范围容易出现精度与边界错误。
- 代价：界面需要把不包含的结束边界转换为用户看到的最后一天，转换和日历运算要测试。UTC 不会自动消除设备时钟误差。
- 重新评估条件：未来任务需要精确到几点几分时，应单独设计截止时刻及其时区语义，不能直接替换现有日期字段含义。

## ADR-008：CUSTOM 加入 v0.1，不做重复任务

- 日期：2026-10-07
- 状态：已采纳。
- 背景：最初讨论 DAY、MONTH、YEAR，用户随后提出未来 5、10、30 天等自定义范围，并确认将其纳入 v0.1。
- 决策：类型扩展为 DAY、MONTH、YEAR、CUSTOM。CUSTOM 输入开始日期和正整数天数，开始日计入总天数，只表示一个完成一次的任务。
- 理由：已有起止日期模型可以容纳该需求，不需重做数据层。单独类型能区分自然月与 30 天，也不会把自定义任务错误归入某个自然周期。
- 页面选择：提供快捷天数和自填输入，展示实际起止日期；CUSTOM 使用独立列表，不自动展开到每天或混入 DAY / MONTH / YEAR 列表。
- 替代方案：把所有任务改成任意范围会削弱自然周期入口；把 CUSTOM 当作每日打卡则需要每次完成记录，超出此次需求。
- 代价：增加表单、类型校验和日期边界测试；不混入每日列表意味着用户需要在自定义入口查看这些任务，这是当前简版的明确边界。
- 重新评估条件：用户需要每日独立完成记录、重复生成或统一今日看板时，分别设计实例模型和跨类型查询，不复用单一 completed_at 冒充完成历史。

## ADR-009：日记自动保存，任务表单手动保存

- 日期：2026-10-07
- 状态：已采纳。
- 背景：日记是持续文字输入，用户明确要求自动保存；任务则有标题、类型和日期范围等应一并确认的表单字段。
- 决策：日记结合输入停顿保存、持续输入周期保存和正常导航前提交；编辑页另提供“保存并返回”作为明确的结束操作，复用导航前提交，不取消自动保存、不另建保存流程。任务表单点击保存才提交。任务完成或删除等独立操作直接持久化。
- 理由：日记不依赖用户记得按保存；“保存并返回”让结束写作的动作明确，并在离页前等待最新内容保存。任务避免将尚未填写完整的范围和标题写入数据库。自动保存结果要与当前编辑版本对应，不能只靠一次写入完成就显示成功。
- 替代方案：仅退出时保存无法覆盖异常结束；每次按键都无条件发起写入会增加队列和状态协调负担；所有表单自动保存会让中间状态处理复杂化。
- 代价：自动保存需要协调定时器、异步写入、页面切换、失败重试和删除。约 800 毫秒停顿、约 5 秒持续输入提交是初始可调整参数，不保证强制结束时最后输入也已落盘。
- 重新评估条件：实际体验证明保存频率不合适时调整参数；如果需要崩溃后恢复每段尚未提交的草稿，应作为额外持久化能力评估。

## ADR-010：软删除与简版日记回收站

- 日期：2026-10-07
- 状态：已采纳。
- 背景：用户确认只做软删除，随后明确要求 v0.1 加入日记恢复和冲突时复制内容的能力。
- 决策：日记和任务都使用 deleted_at 标记删除。日记回收站提供列表、只读详情、恢复、日期冲突提示和手动复制正文；任务暂不提供回收站入口。
- 理由：软删除保留误删恢复和未来传播删除操作所需的信息。日记恢复复用原记录，无需建立另一张内容表。冲突时保留双方内容，由用户决定如何整理。
- 剪贴板选择：只有明确点击“复制正文”才写入剪贴板，复制成功后提示。恢复失败不代表用户想覆盖原来的剪贴板内容。
- 替代方案：硬删除无法支持本次恢复需求；自动合并或覆盖会替用户做内容取舍；单独复制到回收站表会产生两套记录迁移逻辑。
- 代价：所有正常查询需排除已删除记录，自动保存不能让记录复活。v0.1 不提供永久删除、定时清空、批量恢复，数据库会保留已删除内容。
- 重新评估条件：需要存储清理、永久删除或同步删除标记回收时，另定保留和同步确认策略；不能直接定时清除所有 deleted_at 非空记录。

## ADR-011：预留同步基础，不提前实现同步协议

- 日期：2026-10-07
- 状态：已采纳。
- 背景：未来计划多设备同步，但服务端、账号、协议和冲突策略均不属于 v0.1。
- 决策：记录使用本地生成的 UUID v4，保存 created_at、updated_at、deleted_at，读写集中到仓库，并从首版管理数据库迁移。
- 理由：稳定标识允许离线创建；删除标记保留“删除发生过”的事实；仓库边界减少将来引入同步时对 UI 的影响。使用现成 uuid 包生成标识，避免自写随机标识算法。[uuid 文档](https://pub.dev/packages/uuid)
- 暂不添加：无实际同步协议支撑的 is_synced、设备 ID、服务端版本字段，以及空壳同步服务。这些可在设计同步时通过迁移加入。
- 替代方案：仅本地自增 ID 会增加跨设备身份映射工作；预先堆积同步字段并不能解决冲突；只按 updated_at 较新者覆盖，可能受时钟偏差影响并丢失并发编辑。
- 代价：未来仍需设计同步游标、可靠变更追踪、版本比较、冲突保留与删除传播。当前字段不能证明应用已经支持同步。
- 必须处理的未来情形：两台设备为同一天分别创建不同 UUID 的日记；一端删除而另一端编辑；同一篇正文被两端同时修改。
- 重新评估条件：开始实际同步工作时新增完整决策，明确如何迁移现有离线记录，而不是假设服务端已经存在。

## ADR-012：纯文本起步，通过迁移演进内容模型

- 日期：2026-10-07
- 状态：已采纳。
- 背景：用户确认 v0.1 使用纯文本，将来希望加入图片、附件和富文本。
- 决策：正文目前只保存纯文本，不混入预设的富文本结构、图片占位字段或附件二进制。保留稳定日记 UUID 和数据库升级能力。
- 理由：文本编辑和自动保存足以完成第一版核心体验；附件还涉及文件位置、引用和删除，富文本需要明确格式与编辑器，过早设计容易与将来需求不符。
- 替代方案：现在引入富文本编辑器或通用内容块模型，会增加输入法、序列化、迁移和显示测试，当前没有必须承担这些成本的需求。
- 代价：后续需要明确纯文本到新格式的迁移。附件可通过日记 UUID 关联，但具体表和存储方式在相应功能阶段确定。
- 重新评估条件：用户实际安排图片、附件或富文本进入版本范围时，为内容格式和文件生命周期单独记录决策。

## ADR-013：分阶段验收，分别验证两个平台

- 日期：2026-10-07
- 状态：已采纳。
- 背景：项目所有者第一次独立开发完整软件，需要持续看到可用成果并理解文件职责和数据流。
- 决策：按产品文档中的阶段推进，每阶段有明确验收；日记可以先以临时显式保存验证存储闭环，再完成自动保存。双平台尽早跑通，不等 Android 完成后再第一次尝试 Windows。
- 理由：把数据库错误、界面错误和保存调度错误分开排查。小阶段使需求变化容易评估，也便于学习。
- 验证要求：实现后执行相关格式化、静态分析和测试，修复本次变更导致的失败。重点覆盖日期唯一、范围边界、恢复冲突、异步保存和迁移保留数据；发行包也要验证。
- 替代方案：先实现全部功能再统一测试，容易同时暴露多个层次的问题；只验证调试模式或一个平台，不能证明实际双平台交付可用。
- 代价：需要维护少量有意义的测试及数据库样本，但不要求为每个低风险 UI 文案变化编写机械测试。
- 交付说明：每个有意义的功能说明修改了哪些文件、各自职责、数据流和手动验证步骤。文档变更只检查文档，不声称运行不存在的应用测试。
- 重新评估条件：阶段可根据实际依赖调整，但不得通过省略必要验收把尚未验证的功能标记为完成。

## ADR-014：方案 A 框架交付边界与 iOS 候选平台

- 日期：2026-10-08
- 状态：已采纳。
- 背景：用户比较轻量 SQL、Drift 与独立业务层三种方案后，明确选择方案 A，并要求基础结构和数据库表达到可以继续开发具体功能的程度。
- 决策：实现 Android／Windows 官方平台工程、应用组装入口、基本只读列表与导航、模型、SQLite schema v1、基础仓库读写和测试；编辑器、自动保存调度和完整业务按钮按后续阶段实现。
- 理由：数据库约束和仓库读写先独立验证，后续页面可直接调用既有入口；避免先做看似可编辑但不能可靠保存的界面。UUID 由仓库分配，草稿只分配一次并在重试中复用，取得 ID 本身不创建记录。
- 工具选择：直接依赖 sqflite_common 以使用共同数据库 API；flutter_localizations 来自 Flutter SDK，提供中文 Material 文案。未增加第三方状态框架、ORM 或用例层。
- 数据库迁移：初始 schema 为 v1，目前不存在真实历史版本；升级入口保留但未知版本明确失败。以后升版必须增加实际迁移，不能把空回调当作已实现迁移。
- iOS 范围：用户仅表达未来可能适配。保留 iOS 数据库驱动分支并关注依赖兼容性，但本次不生成 iOS 工程，不宣称已支持或验证 iOS。
- 环境边界：使用项目本地、被 Git 忽略的 Flutter SDK 完成生成和测试；不修改全局 PATH。Android SDK 和 Visual Studio C++ 工具链缺失时，明确记录平台运行／发行验证未完成，不把自动化测试当作真机验证。
- 代价：当前界面只能读取列表，完整产品行为要在后续功能阶段实现；使用者仍需配置目标平台原生工具链。手写 SQL 与刷新逻辑由项目维护。
- 重新评估条件：业务复杂度、查询规模或实际跨页面更新需求证明需要新工具时，再有针对性地升级；云同步仍需单独设计协议与冲突处理。

## ADR-015：日记使用轻量自动保存，暂不增加持久化草稿

- 日期：2026-10-09
- 状态：已采纳并实现本阶段新建、内容编辑及自动保存。
- 背景：用户比较手动保存、轻量自动保存和独立持久化草稿后，选择方案 2。验收要求日记写入数据库、重启可读取、编辑保留创建时间和日记日期。
- 决策：保留总体架构 A，增加编辑页面和 ChangeNotifier 编辑状态；状态通过现有仓库的保存回调持久化，直接更新日记表，不添加新依赖或 schema。
- 调度：停顿约 800 毫秒、持续输入约 5 秒提交。每个会话固定 UUID，保存串行执行，仅保留下一次需要提交的最新输入；完成结果与内存编辑版本对应，旧快照成功不能把新内容标为已保存。
- 返回与错误：正常返回冻结输入并等待最新提交；失败保留输入与页面并允许重试。返回统一走提交路径，避免刚输入但尚未重建界面时绕过保存。进入后台和收到退出请求时尽力提交，不能依靠退出通知提供持久化保证。
- 日期：新建草稿在首次保存前可选日期；已保存日记本阶段固定日期，普通编辑不改变创建时间和日记日期。原产品要求的显式修改日记日期仍待后续实现，不以编辑时的当前日期替换它。
- 替代方案：手动保存适合临时验证，但单独保留它不能完成已确定的自动保存要求；独立草稿恢复需额外表、恢复界面及草稿与正文一致性规则，目前没有足够收益。
- 代价：需维护定时器、写入版本及页面生命周期测试。未提交输入只在内存中，强制结束可能丢失最近内容；日期冲突期间也没有独立持久化草稿。内存编辑版本不是同步版本。
- 重新评估条件：用户要求异常结束后恢复未提交草稿时再增加持久化草稿；云同步阶段设计可靠变更追踪与冲突规则，保持本地保存不依赖网络成功。
