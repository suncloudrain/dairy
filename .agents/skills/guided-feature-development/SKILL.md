# Guided Feature Development

本项目的开发目标不仅是完成功能，也包括让项目所有者能够理解
功能的结构、数据流和设计理由。

对于一个有实际业务行为的新功能或重要修改，按照以下流程工作。

不要为了展示“工程化”而增加不必要的抽象、框架或层级。

---

# Phase 1：理解需求

在修改代码之前，先理解用户真正想实现什么。

检查与当前任务有关的：

- `docs/PRODUCT.md`
- `docs/ARCHITECTURE.md`
- `docs/DECISIONS.md`
- 相关现有代码

只读取与当前任务相关的内容，不要无条件阅读整个项目。

首先说明：

1. 这个功能解决什么问题。
2. 用户会怎样使用它。
3. 功能完成后应该表现成什么样。
4. 当前需求中是否存在会影响产品行为的重要歧义。

如果存在重要歧义，不要自己偷偷决定。

---

# Phase 2：描述完整数据流

在写代码之前，用容易理解的方式解释：

用户操作
→ 页面 / Widget
→ 状态或业务逻辑
→ Repository / Service
→ SQLite 或其他数据源
→ 数据返回
→ UI 更新

必须结合当前项目的真实结构，而不是只讲抽象概念。

例如对于“日记自动保存”，需要说明：

- 输入从哪个 Widget 产生；
- 哪个类接收输入变化；
- 什么时候触发保存；
- 哪个 Repository 负责持久化；
- 最终怎样写入 SQLite；
- 保存完成后 UI 是否需要更新。

如果当前项目还不存在其中某一层，应明确说明，
不要为了匹配这个示例强行增加层级。

---

# Phase 3：说明准备修改什么

在实施前列出：

- 准备新增的文件；
- 准备修改的文件；
- 每个文件为什么需要变化；
- 哪些现有文件明确不需要修改。

尽量缩小修改范围。

不要为了完成当前功能顺便进行无关重构。

---

# Phase 4：识别设计决策

判断任务中是否存在需要项目所有者决定的问题。

例如：

- 数据模型如何设计；
- 自动保存什么时候触发；
- 使用什么状态管理方式；
- Repository 是否需要新增接口；
- 数据库 schema 是否需要改变；
- 是否引入新的 package；
- 是否增加新的架构层。

如果存在多个合理方案，不要简单地问：

“你喜欢方案 A 还是方案 B？”

应当进行比较。

对每个方案说明：

- 它解决什么实际问题；
- 当前版本是否真的需要；
- 会增加哪些复杂度；
- 对代码可理解性的影响；
- 将来需求变化时的修改成本；
- 如果现在不用，会留下什么技术债；
- 这个决策以后是否容易改变。

默认遵循：

> 选择能够满足当前真实需求，
> 同时不会给已经明确的未来需求制造高成本障碍的最简单方案。

遵循：

> 为已知变化预留边界，
> 不提前实现未来功能。

例如未来确定需要云同步，可以保留 Repository 边界，
但不要因此提前实现 SyncEngine、ConflictResolver 等当前不需要的系统。

如果简单方案以后很容易替换，优先简单方案。

如果当前选择以后极难改变，则允许投入更多设计成本。

---

# Phase 5：形成实施方案

在编码前给出一个简短实施方案。

方案至少应回答：

- 这次只准备解决什么；
- 数据如何流动；
- 哪些文件会发生变化；
- 是否修改数据库；
- 是否引入依赖；
- 最重要的风险是什么；
- 如何判断这个功能已经完成。

不要输出巨大而形式化的计划。

计划应该让第一次独立开发软件的人也能够理解。

---

# Phase 6：确认门

对于以下情况，在修改代码之前等待项目所有者确认：

- 新功能；
- 数据模型改变；
- 数据库 schema 改变；
- 新增第三方依赖；
- 架构边界改变；
- 存在多个会明显影响未来维护的方案；
- 产品行为存在歧义。

此阶段不要修改代码。

明确告诉项目所有者：

“这是我准备采用的方案。如果确认，我再开始实现。”

对于明显的小修改，例如：

- 拼写错误；
- 单纯文案调整；
- 非结构性的简单样式修正；

不必强制执行完整确认流程。

---

# Phase 7：实施

得到确认后再修改代码。

实施时遵循：

- 只解决已经确认的范围；
- 不擅自增加新功能；
- 不进行无关重构；
- 优先选择容易理解的代码；
- 避免没有实际价值的抽象；
- 遵守现有项目结构；
- Android 和 Windows 兼容性必须纳入考虑。

如果实施过程中发现原方案存在重大问题，
不要偷偷换成另一套架构。

暂停并向项目所有者解释：

- 原方案哪里有问题；
- 为什么需要改变；
- 建议的新方案是什么。

---

# Phase 8：验证

实现以后不要以“代码已经写完”作为完成标准。

运行与当前修改相关的检查，例如：

- formatter；
- static analysis；
- unit tests；
- widget tests；
- database tests。

只运行与项目实际存在的工具相匹配的命令。

如果测试失败：

- 判断是否由当前修改导致；
- 如果是，则修复；
- 如果不是，说明这是已有问题，不要偷偷修改无关代码。

然后提供人工验收步骤。

人工验收步骤必须站在用户角度描述。

例如：

1. 打开日记列表。
2. 点击“+”。
3. 输入正文。
4. 返回列表。
5. 关闭应用。
6. 重新启动。
7. 确认日记仍然存在。

---

# Phase 9：开发者交接

功能完成以后，用教学式但简洁的方式解释实现。

必须说明：

## 修改了什么

说明新增和修改的重要文件。

## 每个文件负责什么

对于重要文件，用一句话说明：

- 它负责什么；
- 它不应该负责什么。

## 完整调用链

按照实际代码说明：

用户操作
→ Widget
→ 状态 / Controller / ViewModel
→ Repository
→ Database
→ 返回
→ UI 更新

指出真实类名、方法名和文件路径。

## 为什么这样设计

只解释本次实现中真正重要的设计决定。

不要泛泛讲软件工程理论。

## 如何自己验证

给出项目所有者可以实际执行的验证步骤。

---

# Phase 10：知识检查

对于明显具有学习价值的新功能，
最后给项目所有者 2～4 个简短问题。

问题应检查其是否理解本次真实实现。

例如：

- 为什么 `createdAt` 在编辑日记时不应该变化？
- 从输入框输入文字到 SQLite 写入，中间经过了哪些对象？
- 如果未来改成云同步，当前哪个边界最可能发生变化？

不要把它变成考试。

目的只是帮助项目所有者发现自己哪里还没有理解。

---

# Phase 11：文档维护

只有实际发生变化时才更新文档。

如果产品行为或范围发生变化：
更新 `docs/PRODUCT.md`。

如果项目结构、模块职责或主要数据流发生变化：
更新 `docs/ARCHITECTURE.md`。

如果做出了值得长期保留理由的重要技术决定：
更新 `docs/DECISIONS.md`。

不要因为每个小修改都机械更新所有文档。

---

# General Principles

始终优先：

简单 > 不必要的复杂

清晰 > 炫技

真实需求 > 假想需求

可理解 > 过度抽象

完成一个可验证的小功能 > 同时铺开多个未完成功能

保留未来变化的边界 > 提前实现未来

项目所有者理解代码 > AI 单纯把代码写出来
